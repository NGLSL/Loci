# 来源、对象、目录项与平台游标

Status: proposed

本记录是 Windows 独立原型向共享核心提出的契约建议，尚未得到 Linux／共享核心会话确认。阶段 B 可以验证下述私有模型；共享引擎装配以双方接受后的 ADR 为前提。

同一对象可能有多个硬链接，完整路径还会随祖先目录改名变化，因此完整路径不能作为对象的唯一身份。采用来源身份、来源内对象身份及独立目录项关系：每个目录项保存 parent、object 与平台原始 name，搜索路径从目录关系派生。Windows 原始名称保留 UTF-16 码元；Linux 名称保留字节的建议待对应实现确认。显示或查询转换不能改写原始名称。

Windows 原型的来源绑定由卷 GUID、既有 API 提供的 legacy 32-bit volume serial 和选定根对象共同组成；serial 的存储位宽不代表已验证完整 64-bit 卷序列号。对象 file reference 保留其完整返回值及复用区分信息。对象和父对象必须属于同一来源。硬链接的每个搜索路径拥有自己的目录项，USN 单次枚举记录不能代表全部链接名称；实际命名空间和原生硬链接枚举需要共同核对。

阶段 B 的私有 EntryId 暂采用 `(parent, object, raw name)` 关系键，改名相当于删除旧关系并添加新关系。共享 EntryId 是否跨改名保持稳定、跨删除重建如何避免身份复用，以及持久键的编码，仍待共享确认；本提案没有冻结公共接口。

游标属于平台来源。Windows 保存 journal ID 与 USN；Linux 提供自己的 opaque provider cursor，不能假定具备 USN 的全局顺序或持久恢复语义。来源 identity、完整 inventory 与对应 cursor 在同一次原子持久更新中发布；任何重放、权限、预算或一致性校验失败都保留旧有效状态并报告 Pending／要求重建。journal ID 改变、已保留范围不覆盖游标及游标超出当前边界分别返回明确原因。

选择关系模型增加了路径解析与一致性检查的成本，但避免改名重写所有后代主键及硬链接路径丢失。把完整路径作为缓存可以是后续优化，不能替代来源、对象及目录项的身份关系。小型原型中的稳定截止点校验不等于并发任意写入下的文件系统事务快照，也不提供真实掉电或跨平台保证。
